DESIGN RECORD

Architecture & methodology

OmniRouter separates task classification, supervisor policy, and model assignment. A request receives a minimum application tier, TL0 through TL3, then maps to the configured answering model or a human-support queue. Each decision records the evidence, policy snapshot, and execution history needed for review.

Fictional query→Classifier + guardrails→Minimum tier or handoff→Configured model→Execution audit

Classification and protected floors

Deterministic routing evaluates enabled patterns and supervisor phrases; the highest matching tier wins. Unknown intent uses the configured fallback. Urgency can raise the minimum, while protected emergency signals force TL3. Mandatory case-specific TL3 rules cannot be disabled or lowered.

Live Support also supports an LLM classifier. It proposes a tier, rationale, exact quoted evidence, and a human-review flag. The backend validates the result and applies deterministic floors. A classification failure stops execution. Supervisor handoff conditions take precedence and skip model calls; a review flag alone does not contact a human agent.

One family, four configurable model assignments

In Routing configuration, the Tier models tab selects one family for all four tiers: OpenAI, Anthropic, Google, or Grok. Each tier has a dropdown of that family's text chat models from a bundled OpenRouter catalog snapshot. Admins can assign any listed model to a tier or use the same model for several tiers. Suggested TL labels follow model-variant heuristics and need validation against the actual workload.

Tier names describe task categories: TL0 document navigation, TL1 benefits and comparisons, TL2 interacting provisions, and TL3 case-specific coverage and appeals. They do not establish a model's measured quality or price. A backend-default selection uses the corresponding server model setting; previously saved model IDs remain visible if absent from the catalog.

Saving, publication, and accountability

Save simulation preferences at the bottom of Tier models persists the four model assignments in this browser and records an automatic change reason. Other routing-policy changes use the apply controls and require a supervisor name and reason. Local saves affect future simulation policy snapshots; Publish policy, with separate supervisor credentials, activates changes on the live backend. Existing decisions retain their original snapshots.

Live answering models use published tier assignments, with backend settings as fallbacks. The optional LLM classifier has its own model configuration and cost. Live audits record the requested and returned model, routing evidence, effective model configuration, provider usage, available costs, and execution timing.

Costs depend on the selected models

There is no universal dollar price for TL0, TL1, TL2, or TL3. Live costs depend on the model family, specific model, provider pricing, input and output usage, and additional executions. Assigning one model to several tiers does not create different per-token prices for that model.

For planning, estimate each answering call as input tokens × input rate plus output tokens × output rate, using consistent rate units. Add classifier calls, retries, reassignments, and evaluation comparisons. Use current rates for the selected models and record when they were checked; the dropdown catalog and suggested tier labels are not a price quote.

The simulation dashboard currently uses fixed illustrative tier prices. Changing the selected family or models does not update those dollar estimates. Its routing surcharge and latency assumptions are also fixed examples. Dashboard totals and savings explain routing mechanics; they are not forecasts for the saved model preferences.

Live Support shows provider-reported answering costs and separately records classifier cost when available. Missing usage or cost stays unavailable, and cumulative known cost is marked incomplete when necessary. Human handoff skips model execution, but human labor and resolution time are excluded from the displayed model costs. Savings can be negative when classification and additional executions outweigh a cheaper initial assignment.

Simulation and response methodology

Compare a fixed-tier baseline with deterministic routing using the same request count and workload seed. Input and output token counts are synthetic; input estimates use query length plus a fixed context allowance. The browser batch simulator makes no provider calls and cannot run the LLM classifier.

Required tiers are authored independently of routing decisions. The quality illustration assumes a 96% score at or above the required tier, subtracting 18 percentage points per tier below it, with a 10% floor. These are assumptions rather than graded model responses. Audit comparisons show authored response illustrations for two selected tiers. Playback speed and assumed response latency are separate from measured backend execution time.

Interventions and controlled comparisons

Simulation reassignments require reasons; below-minimum downgrades require the demo supervisor role. Each reassignment models an additional execution and cost. Live operational reassignment blocks tiers below the routing minimum. Controlled live comparisons preserve the original query, policy context, and answering request while changing the model. Selecting a different tier with the same model does not provide a distinct model comparison.

Workload provenance and fictional policy

Forty-five percent of a batch consists of repeated fictional adaptations of two public case summaries; the remainder uses sixteen authored scenarios with seeded variations. The mix is rounded for small batches. It is not a representative dataset of customer conversations. Scenarios cover plan documents, comparisons, referrals, network rules, exclusions, and appeals.

Kaggle HHS Health Insurance Marketplace and CMS public-use files are domain references. Harbor Health Demo Handbook v1.0 supplies fictional plan documents, benefits, referral and network rules, and exceptions and appeals. These fixtures do not establish real coverage or state-specific rules.

Evaluation and production requirements

Before comparing families or model assignments, run a held-out fictional sample against the actual configured models. Grade factual accuracy, policy grounding, completeness, and appropriate escalation, and retain model IDs, policy versions, usage, costs, and timings. Report those measurements separately from simulation assumptions.

Browser roles, browser storage, and backend JSONL records are demonstration controls. Production use would require individual identities, stronger authorization, protected policy retrieval, durable audit integrity, service-desk integration, and workload-specific evaluations. Provider credentials belong on the backend.
